# Feature Plan: POLE+O ontology refactor + facts + preference supersession (Phases 2–5)

## Summary

Pick up `plan.md` where Phase 1 (multi-tenancy foundation, merged in PR #18 / commit `9bdc616`) left off and ship Phases 2–5 of the POLE+O port as a single coordinated feature on `feat/pole-o-ontology-refactor`. Phase 2 is a small conversation-ingestion polish pass (define `source_uri` semantics, kill dead "structured messages" code, optional `metadata.session_started_at`). Phase 3 is the big one — replace the closed `NodeType` / `EdgeType` enums with a `NODE_REGISTRY` + `register_node_type` / `register_node_subtype` extension API; add the full POLE+O canonical node-type set (`person`, `organization`, `location`, `event`, `object`); collapse the 14 POLE+O domain edges into a single `related_to` edge discriminated by `semantic_type` (validated against a `RELATION_SEMANTICS` registry — strict envelope, lenient field-level); register Tree's `task` / `episode` / `topic` / `project` as **subtype extensions**, not canonical POLE+O subtypes (Tree is its own first customer of the extension API); add `ExtractorInfo` provenance metadata, `subtype` / `description` / `valid_from` / `valid_until` / `semantic_type` columns on `KnowledgeGraphEntry`; broaden `mentions` (chunk → any POLE+O entity) and `same_as` (any POLE+O entity → same type); add structural-edge property models (`MentionsProperties`, `SameAsProperties`); and surface `extraction_rejections` + `extraction_dropped_fields` audit collections. Phase 4 adds the `fact` escape-hatch node — island-style (zero edges to or from it, retrieved by vector / string lookup only). Phase 5 turns the existing free-form `PreferenceProperties` (`content: str`) into typed slots (`statement` / `category` / `target` / `over` / `context` / `strength`) with a closed `PreferenceCategory` enum, adds a resolver-written `superseded_by` edge (preference→preference, never LLM-emitted) plus a contradiction-judge branch, generalizes bi-temporal supersession to `fact`, enforces the "preferences attach only to `person:self`" rule, and surfaces a three-tier `DedupConfig` (`auto_merge_threshold` / `flag_threshold` / `fuzzy_threshold` / `match_same_type_only`) under `tree.config.settings`. Migration follows the Phase-1 convention: wipe-and-rebuild — drop `knowledge_graph`, re-run extraction + indexing for the seed user under the new schema. Phase 6 (provenance edges as a graph layer) is **deferred** — `plan.md:559–561` explicitly says "Skip until needed" and today's `KnowledgeGraphEntry.sources: list[ObjectId]` answers every query we have; it returns when a concrete "which entities did this single message produce?" query arrives. The Phase-1 two-user isolation test continues to be the standing acceptance gate; three new end-to-end ACs (POLE+O multi-type paragraph → correct `related_to` semantics; contradictory preferences → `superseded_by`; free-text fact → zero edges) live in the migration / verification task.

## Migration story

**Wipe-and-rebuild**, mirroring the Phase-1 convention (`plan.md:436–438` migration note; the existing `scripts/migrate_multi_tenancy.py` template).

Why wipe-and-rebuild over in-place rewrite:

1. `KnowledgeGraphEntry.type` changes from a closed `NodeType | EdgeType` union to free `str` validated against `NODE_REGISTRY`. An in-place rewrite would need a custom Beanie deserializer just for the migration window.
2. Every `NodeType.TASK` row needs `type="object"` + `subtype="task"`; every `NodeType.EPISODE` row needs `type="event"` + `subtype="episode"`. That's an in-place schema rewrite plus an aliases / properties carry-over.
3. The three LLM-extractable domain edges (`TODO`, `EXPERIENCED`) need to be re-emitted as `related_to` rows with a `semantic_type` discriminator. Existing `HAS` edges stay as a structural edge (renamed slightly — `has: person:self → preference` survives Phase 3 unchanged per `plan.md:469–474`).
4. Old row `properties` payloads don't carry `subtype` / `description` / `valid_from` / `valid_until` / `extractor` / `semantic_type`. They'd all be defaulted but the migration validation matrix is non-trivial.
5. Phase 1 already established the precedent: drop `knowledge_graph`, re-run extraction. The dev data set is small. The full extraction pipeline is idempotent + checkpointed + retryable.

Migration is its own task — **#033** — not folded into #028 or #029. The script extends (or forks under a new sibling name like `migrate_pole_o_ontology.py` — final naming decided in #033's grooming) `apps/memory/scripts/migrate_multi_tenancy.py`:

1. Find the seed `User` (re-use Phase-1's by `--identifier`).
2. Drop `knowledge_graph` collection.
3. Re-create `person:self` node for the seed user (single `setOnInsert` upsert — the User `after_insert` hook does this, but the user already exists, so we call the hook explicitly post-drop, mirroring Phase 1's step 4).
4. Drop `extraction_rejections` and `extraction_dropped_fields` collections too (these collections did not exist pre-Phase-3; if a re-run is happening, they're stale).
5. Trigger `memory-extraction-etl` + `memory-indexing-etl` deployments for the seed user.

Idempotent in the same sense as Phase 1: re-running with the same `--identifier` is a no-op after step 1 finds the existing user.

## Out of scope (intentional)

- **Phase 6 — provenance edges as a graph layer.** `plan.md:559–561` explicitly defers this: *"Skip until needed."* Today's `KnowledgeGraphEntry.sources: list[ObjectId]` answers every provenance query the agent surfaces (find the chunks for a node, the document for a chunk, the conversation Document for a chunk). The trigger to revisit is a concrete query that this list cannot answer — `plan.md:559–561` gives the canonical example: *"which entities did this single message produce?"* — i.e., needing a per-source edge with extraction-time metadata rather than a flat list. None of Phases 2–5 introduces that query. Stays deferred; revisit on demand.
- **Structured `{role, content}` message ingestion + `messages` collection.** `plan.md:93–95` defers this behind a real source that delivers reliably-delimited turns (Slack export, OpenAI API logs). Conversations remain a `Document(source_type=CONVERSATION)` with raw text content.
- **`applies_to` edge from `preference` to entity** (e.g., "I prefer vegetarian *at Italian restaurants*"). `plan.md:476–478` keeps scoping inside `PreferenceProperties.context` (free-text), not as a graph edge. Adding the edge later is a strict superset; nothing in this feature blocks it.
- **`part_of_project` edge from `task` to `project`.** `plan.md:182` explicitly skips this — task/project relationships live in the user's external task manager, not the KG.
- **Reasoning layer, hybrid extractors (regex/spaCy), dynamic node labels, spatial Point indexes, Wikipedia/Wikidata enrichment, DB-persisted `:Schema` config, `:Extractor` provenance node + `EXTRACTED_BY` edge.** All confirmed-skip in `plan.md:563–571`.
- **LLM-prompt evaluation harness comparing extraction quality before vs. after the prompt grows.** `plan.md:302` notes this would be "worth an eval" but does not block Phase 3 acceptance. The lenient field-level validator + `extraction_dropped_fields` audit collection give us the post-hoc signal we need to spot prompt degradation in dev runs.
- **A separate `applies_to` / `mentioned_in_chunk` *broadcast* index on `MentionsProperties.start_pos` / `end_pos`.** The mention-position fields are stored (so a future "highlight in chunk text" UX has the data) but no index is added — there's no current query.
- **Three-tier `DedupConfig` thresholds exposed via the MCP server.** `DedupConfig` lives under `tree.config.settings` and is reload-on-process-start, not request-scoped. A per-tenant override is a follow-up.

## Open questions

None blocking. Two tactical calls the SWE may make during implementation without re-engaging PM:

- **Final naming for the Phase-3 migration script** (`scripts/migrate_pole_o_ontology.py` vs. extending `scripts/migrate_multi_tenancy.py` with a `--phase` flag vs. a single `scripts/migrate.py` umbrella). Keeps one entry point.
